# 调研记录

## 审阅摘要

- 调研缘由：用户决定跳过原计划的 M3 快捷入口，直接实现 v2 精准遮挡，并把"整块遮挡"和"精准遮挡"做成可选的两种模式。
- 目标：默认行为不变；新增"精准遮挡"模式，锁定时只露出白名单聊天所在的行，其余照旧遮住。
- 已确认结论：Q-001～Q-010 均已由用户在 2026-09-30 回复，全部采用建议方案。D-011 所列推导规则用户未提出异议。实施阶段用真实数据验证时发现四处方案冲突（Q-012～Q-015），都已由用户决定（D-013～D-018）。
- 范围与边界：只做 macOS；白名单按聊天名称定义；不做快捷入口、不按置顶识别、不做 Windows 版。
- Blocking 问题：无。Q-001～Q-010、Q-012～Q-015 均为 `ANSWERED`；Q-011 是 Non-blocking 的优化建议，仍为 `OPEN`。
- 两轮探测的结论（见"探测记录"）：原方案的单窗口流加 `sourceRect` 可用，但微信窗口会一直带着紫色的共享标记，用户不接受（D-016）。改为定时取静帧，每 0.2 秒一张，没有标记也没有菜单栏指示，代价是读取画面期间持续占用 CPU（D-017）。变化检测改为比较各格相对底色的偏差，避免悬停被误判（D-018）。
- 下一步条件：按改写后的 design 继续 tasks 4.2 及之后的任务。

## 需求理解

### 已确认行为

- [USER] 不做 M3 快捷入口（S-01 第 1 条）。
- [USER] 实现 v2 精准遮挡，采用白名单策略（S-01 第 2 条）。
- [USER] 两种模式由用户选择：默认是"整块遮挡"，即当前实现；只有选择"精准遮挡"时才需要提供白名单（S-01 第 3 条）。
- [USER] Q-001～Q-010 的决策见"决策记录"D-001～D-010；推导规则见 D-011。

### 验收标准

1. 默认模式为整块遮挡。已有用户升级后行为不变，包括没有新字段的旧配置文件（D-011）。
2. 可以在菜单里切换两种模式；切换立即生效，重启后保持；锁定时也能切换（D-004、D-005）。
3. 精准遮挡、处于锁定、已授予屏幕录制权限时，列表栏里只有白名单聊天所在的行露出，这些行可以直接点击；其余区域照旧遮住（D-001）。
4. 名称匹配符合 D-002 的规则，截断的判定按 D-013。
5. 列表内容一变化（滚动、新消息把聊天顶上来、切到通讯录等），已露出的行在 0.3 秒内重新盖住；画面稳定、识别完成后再露出。悬停不算内容变化；选中一行后，已露出的行重新盖住、识别完成后再露出（D-003、D-012、D-014）。
6. 精准遮挡下，密码框固定在列表栏底部的遮挡条里，始终可用（D-006）。
7. 精准遮挡下，白名单为空或没有屏幕录制权限时，表现为整块遮住；缺权限时菜单给出提示和授权入口（D-008、D-011）。
8. 编辑白名单需要先解锁。第一次切到精准遮挡、白名单为空且处于解锁状态时，自动打开编辑窗口（D-004、D-005、D-012）。
9. 两种模式各自保存校准结果。精准遮挡第一次使用时，沿用整块遮挡的左右边界，上边距为 0（D-007）。
10. 不保存截图，日志里不记录聊天名称；README 的隐私说明、架构文档和配置 schema 同步更新（D-009、D-011）。

### 范围内

- 遮挡方式的选择与持久化；白名单编辑与持久化；精准遮挡的截图、识别、匹配、露出与重新遮住。
- 屏幕录制权限的检测、申请和缺失时的退化行为；精准遮挡的独立校准；精准遮挡下密码框的位置。
- 架构文档、README、配置 schema 的更新，以及删除 M3 快捷入口的相关描述。

### 范围外

- 快捷入口（M3）；按置顶底色识别白名单（Q-001 的 B、C 选项）；黑名单模式。
- Windows 版的实现，只在架构文档中保留对应关系。
- 名单编辑之外的通用设置窗口（Q-004 的 B 选项）。
- 截图样本入库（D-010）。

## 探测记录

第一轮，2026-09-30，用户本机（macOS 26.5，微信 4.1，内建显示器 2 倍分辨率）。微信主窗口 1171×822 pt，列表栏取窗口坐标 (60, 0, 242, 766)。

| ID | 探测内容 | 结果 |
| --- | --- | --- |
| P-01 | 单窗口流 + `sourceRect`（窗口坐标，1 倍分辨率） | 裁剪生效：与整窗画面里的列表栏平均差 0.76（与整窗缩小后的平均差为 36.36）。随帧信息 contentScale=0.5、scaleFactor=2.0。起始 10 帧之后，画面静止时不再推帧。Apple 文档"单窗口截图不使用 `sourceRect`"在这个系统版本上不成立；macOS 14、15 上未验证 |
| P-02 | 单窗口流，整窗 | 约 11 秒 113 帧，全部是完整帧：窗口内任何位置有变化都会推帧 |
| P-03 | 紫色共享标记（用户目测） | 单窗口流：有。按显示器且只包含微信窗口、或只包含微信应用：有。按显示器且排除其他所有应用：没有。单窗口静帧连取 5 张：没有闪烁。截图期间菜单栏有录屏指示 |
| P-04 | 按显示器截图 + `sourceRect` 的裁剪是否正确 | 没有结论：脚本按 ScreenCaptureKit 报告的窗口位置计算裁剪区域，而这个位置不准（P-05） |
| P-05 | `SCWindow.frame` 与 `SCContentFilter.contentRect` | 位置不可靠：相隔 30 分钟的两次运行都报告 (180, 74)，窗口服务器和随帧的 screenRect 都是 (233, 57)，用户确认没有挪动窗口。尺寸一致。几何信息一律以窗口服务器（CGWindowList）为准 |
| P-06 | 悬停、点击、滚动（整窗流，取列表栏部分算指纹） | 悬停 5 次：底色亮度 +5～+11，每条最多 2 格不同，都没有判为变化。点击选中 26～29 格、滚动 34～40 格，都判为变化 |
| P-07 | 列表栏的文字框（2 倍分辨率） | 识别耗时 436 ms。11 行全部切对；行距 65 pt，名称与预览的上边缘相差约 21.4 pt；算出的带区都落在真实行内，偏差不超过 1.5 pt。两个截断的名称末尾都被识别成 `..`。时间和未读角标是独立的文字框，不与名称合并 |
| P-08 | 在命令行程序里创建单窗口过滤器 | 要先建立与窗口服务器的连接（调用一次 `CGMainDisplayID()`），否则 CoreGraphics 断言失败。应用有 `NSApplication`，不受影响 |

## 变更影响

### 受影响区域与接口

- [CODE] Core：`AppConfig` 新增字段及 `shared/config.schema.json`；`MaskPlanner` 的洞增加白名单行来源，并保留底部遮挡条。新增纯逻辑：名称匹配、由识别结果切分行、画面变化指纹、"先遮后露"状态。
- [INFERENCE] 新增识别模块：用 Vision 做文字识别，放在本地包的新 target 中，以便 `swift test` 覆盖。
- [INFERENCE] 应用外壳新增：ScreenCaptureKit 截图、屏幕录制权限、白名单编辑窗口、精准遮挡流程控制。需要修改：`MaskController`、`MaskView`（底部遮挡条、按模式选择布局）、`AppDelegate`、`StatusMenuController`。
- [CODE] 文档：`docs/architecture.md`、`README.md`。

### 共享使用方与回归范围

- 整块遮挡的全部行为必须保持不变：遮罩几何、给其他窗口开洞、密码框、校准、锁定规则、跨桌面、调度中心。
- 回归方式：现有 Core 单测，加上 M1、M2 的手动验收清单在整块遮挡模式下复测。

### 兼容性与运行关注项

- 配置向后兼容：新字段缺失时，分别取整块遮挡、空白名单、从整块布局推导。`schemaVersion` 不变。
- 屏幕录制权限：发布包是临时签名，每次升级后都要重新授权，这点和辅助功能一样（S-05）。[INFERENCE] macOS 15 起，不经系统选择器直接截屏的应用会被定期要求重新确认，需要在 macOS 26 上实测。
- 资源占用：只在"精准遮挡 + 锁定 + 微信窗口可见 + 已授权 + 白名单非空"时截图；画面不变时系统不推送新帧。
- 隐私：精准遮挡会读取列表区域的画面，只在内存中识别，不落盘、不联网；README 需要如实说明。
